Gossip 與 Memberlist

發表於 2025-03-10 分類於 cloudnative 閱讀次數：

分散式系統如何偕同工作一直是個有趣的議題，當接觸越多專案，可能就會發現有些簡單好用的模組會被大量使用。就像memberlist，他是基於Gossip協議的Go library ，用來管理集群成員關係、節點狀態同步和成員故障檢測，用在像是Consul、Cortex、Loki、AlertManager、Redis…

source code: https://github.com/hashicorp/memberlist

在繼續探討以前，我們還是需要先來了解一下 Gossip 協議

Gossip Protocol

一傳十 十傳百!
又稱為Epidemic Protocol，可想像同一個病房裡，病毒會開始從一個人身上隨機傳染給多人，到最後都會染病。對應到這邊就是同一網路的節點隨機傳播時，每個節點最終會保持一致的狀態。

具體行為:

  • 節點 (Nodes)：圖上有多個節點，代表每一個參與 Gossip 協議的成員。
  • 通信 (Communication)：每個節點都會隨機選擇其他幾個節點進行通信。
  • 訊息傳遞 (Message Propagation)：當某個節點收到一條訊息後，它會再次隨機選擇其他節點傳播該訊息。這個過程會持續進行，直到訊息傳播到所有節點為止。

常見的協議方式有三種:

  1. Push: 集群中節點A收到一條訊息後，會隨機從集群中挑選一個或多個節點，比如發送至節點B，B也會進行同樣操作，但不會再次選擇節點A
  2. Pull: 節點A定期從集群中隨機選擇一個或多個點，然後發起請求Pull 訊息，如有新訊息則會同步。
  3. Pull+Push

收斂的速度: 從有新訊息在一個節點到所有節點狀態都為一致，是為收斂的速度。協議可以配置各節點行為來決定收斂的速度。比如每個節點都要拉全部節點的訊息，同時也Push自己的訊息到全部節點，這樣收斂的速度最快，但最費頻寬。所以一般還是以隨機節點的同步為主。

此協議的好處為

  1. 擴展性: 節點可任意加入或退出，不影響最終集群內每個節點的狀態。
  2. 容錯: 同樣，萬一有節點壞掉，也不影響最終集群內每個節點的狀態。
  3. 去中心化: Gossip不需要中心節點，每個節點都是對等。
  4. 最終一致性: 集群內節點最後會收斂成同一狀態。

當然也有缺點:

  1. 消息延遲: 可能節點收到的訊息會有時間差，故這不適合用在即時性較高的系統。
  2. 消息重複傳遞
